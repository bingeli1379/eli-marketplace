# setup

Produces `knowledge.config.json` in the repository that will hold the knowledge base. Every other skill and the renderer read that file. Its fields and what each drives are in `${CLAUDE_PLUGIN_ROOT}/schema/config.reference.yaml`; the choices offered per question are in `${CLAUDE_PLUGIN_ROOT}/schema/presets.json`.

## The config file

- It lives at `<repo>/knowledge.config.json`.
- Only this skill writes it; the renderer reads it and never modifies it.
- A missing file is a first run. An existing file is a revision: its values are the proposal for every field, and the run changes only what the user asks to change.

## Steps

1. **Find the repository and the mode.** Take the argument as the repository path or the config path; with none, ask for the repository path, offering the current directory by its full path. Run `python3 --version`; the validator in step 5, validate a draft, needs Python 3, so without it stop and name that requirement. Records the repository path and the mode (first run or revision), which step 3, probe the repositories, and step 6, write the config, consume. Done when the directory exists and the mode is stated to the user. A missing directory is created only if the user agrees; if they decline, stop.
2. **Read the field list and the presets.** Read both files named above now; each holds what the later steps offer or fill. If either cannot be read, stop and say the plugin installation is incomplete.
3. **Probe the repositories before asking about them.** Ask for the folder that holds the source repositories (`paths.repos_root`, with its `ask:` wording) unless the existing config has it. Look at a bounded sample of repositories in that folder, spread at an even stride across it rather than the first few (names cluster by project kind, so an alphabetical head shows one stack), and say how many were looked at. From what they show, propose every field the reference marks `(not asked: …)` plus the environments: git host, the four stack areas, the environment names in the deploy files (and any the proposal leaves out), whether database projects or migration files exist, and the team names the repositories carry. In a revision, probe only the fields the config leaves empty, or every field when the user asks to detect again. Propose connected tools only from the tools this session can see, and say when it cannot tell. Records a proposal table of field, value and the file or tool it came from, which step 4, settle the config, consumes. Done when every proposed value cites its source; a field with no evidence stays out of the table. An empty or missing folder is stated, and every field with an `ask:` line is then asked.
4. **Settle the config, asking only what step 3 could not.** A field the reference marks `(not asked: …)` takes the proposal table's value, the stated default, or step 1; it is never a question, and step 7, hand off, lists it. `paths.repo` is the path from step 1 and `paths.repos_root` the folder from step 3. The fields carrying an `ask:` line are asked in this order, one batch each: skill name, what to call the knowledge and the id people sign notes with; the user's own team; project kinds; environments; the runtime when step 3 found none; connected tools; reader examples. Connected tools is one confirmation covering logs, dashboards, the feature-toggle lookup and the wiki, not a question per tool. It is asked only when step 3 found at least one candidate tool; otherwise every capability is `none` and step 7 lists them. Its answer supplies `global_settings.lookup` and `external_reference.sources`; a capability the user names no source for is `none`. Ask each question in the user's own language and plain words, built from the reference's `ask:` and `effect:` lines: the question, then one clause on what the answer changes in the generated files, with every choice described by what it means for them. A config key, a preset slug that is not the thing's everyday name, and a term of this skill (reachable, deployed, skeleton, capability) never stand as the question or a choice label. Present a single proposed value for confirmation inside its batch, with its evidence in plain words. A question with a finite answer set offers the presets, named in everyday words, plus an other choice. The skill name question shows the full name the answer produces (`<name>-knowledge`). A capability the user does not have is set to `none`, which removes its sections from the output. Every team is `reachable` unless the user says some repository cannot be cloned; only a team they cannot read is a candidate for `(external: …)`. A team's `code` is its label in capitals unless a repository names one, and teams step 3 found in repositories are confirmed in the team batch. A field with no evidence in step 3 takes the reference default: `git.host` is `other`, a stack area is `presets: []`. In a revision, keys the reference no longer lists are dropped. Take the audit and kit tuning fields from the reference defaults and list them in step 7 instead of asking. Records the config object, which step 5, validate a draft, validates. Done when every required field in the reference holds a value that is either confirmed or a stated default, and no question was asked about a fact step 3's proposal table already holds.
5. **Validate a draft.** Write the object to a scratch file and run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/render.py" --config <scratch file>`. Without `--write` the renderer only validates and prints a plan, so nothing is written. Fix every error answerable from what the run already knows; ask only when the answer is the user's knowledge. Done when it exits 0.
6. **Write the config.** When the file already exists, show the difference from the draft and wait for confirmation before replacing it; when it does not, write it. Done when the same command on `<repo>/knowledge.config.json` exits 0; cite its `plan:` line.
7. **Hand off.** Report the path written, the fields decided without a question (default or probe, each with its source), and the answers the user was unsure of, then name `/knowledge-generator:generate` as the next command. Nothing is rendered here. Done when the report contains all three.

Running this again on an unchanged config and accepting every proposal produces the same file.
