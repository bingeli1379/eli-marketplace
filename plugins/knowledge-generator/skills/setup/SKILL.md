# setup

Produces `knowledge.config.json` in the repository that will hold the knowledge base. Every other skill and the renderer read that file. Its fields and what each drives are in `${CLAUDE_PLUGIN_ROOT}/schema/config.reference.yaml`; the choices offered per question are in `${CLAUDE_PLUGIN_ROOT}/schema/presets.json`.

## The config file

- It lives at `<repo>/knowledge.config.json`.
- Only this skill writes it; the renderer reads it and never modifies it.
- A missing file is a first run. An existing file is a revision: its values are the proposal for every field, and the run changes only what the user asks to change.

## Steps

1. **Find the repository and the mode.** Take the argument as the repository path or the config path; with none, the current directory, whose full path is stated with the mode. Run `python3 --version`; the validator in step 5, validate a draft, needs Python 3, so without it stop and name that requirement. Records the repository path and the mode (first run or revision), which step 3, probe the repositories, and step 6, write the config, consume. Done when the directory exists and the mode is stated to the user. A missing directory is created only if the user agrees; if they decline, stop.
2. **Read the field list and the presets.** Read both files named above now; each holds what the later steps offer or fill. If either cannot be read, stop and say the plugin installation is incomplete.
3. **Probe the repositories before asking about them.** Ask for the folder that holds the source repositories (`paths.repos_root`, with its `ask:` wording) unless the existing config has it. Look at a sample of about 30 repositories in that folder (all of them when there are fewer), spread at an even stride across it rather than the first few (names cluster by project kind, so an alphabetical head shows one stack), and say how many were looked at. A fact that one directory listing or one field read per repository settles (e.g. the environment names in deploy files, the places that name an owner with the team values they carry, the database folders of each database project) is read over every repository in the folder instead, because a sample of that size drops teams and keeps an environment that fewer than half of all deploy files name. Propose every field the reference marks `(not asked: …)` plus the environments: from the sample, the git host, the four stack areas, whether migration files exist and the repositories with the most recent commits; from the full read, the environment names in the deploy files (and any the proposal leaves out), whether database projects exist with the database folders each one holds, and the places that name an owner (a file or an annotation), each with how many repositories it covers and the team values it carries. In a revision, probe only the fields the config leaves empty, or every field when the user asks to detect again. Propose connected tools only from the tools this session can see, and say when it cannot tell. Make one call to each candidate tool that returns at most one record or one count (a listing of everything is not that); one that errors or times out is recorded as unreachable in the proposal table, so step 4's connected-tools question can name it and the user can restore the connection before the authoring commands run. Records a proposal table of field, value and the file or tool it came from, which step 4, settle the config, consumes. Done when every proposed value cites its source; a field with no evidence stays out of the table. An empty or missing folder is stated, and step 4's rule for a field with no evidence then applies to every field.
4. **Settle the config, asking only what step 3 could not.** Records the config object, which step 5, validate a draft, validates. Done when every required field in the reference holds a value that is either confirmed or a stated default, and no question asks the user to supply a fact step 3's proposal table already holds; confirming a proposed value is allowed.
   - **Decided, never asked.** A field the reference marks `(not asked: …)` takes the proposal table's value, the stated default, or step 1; step 7, hand off, lists it. `paths.repo` is the path from step 1 and `paths.repos_root` the folder from step 3. A field with no evidence in step 3 takes the reference default: `git.host` is `other`, a stack area other than the runtime is `presets: []`. The audit and kit tuning fields take the reference defaults. `scope.owners` is every team value step 3 found in the chosen ownership place (in any place when the user chose to be asked per project), values equal ignoring case counting once, each `code` the value in capitals and each `label` the value as found. When no team value was found (no place, a place the user typed that step 3 did not find, or a place without team values), the user names the team in the Asked block, and its `code` is the name in capitals. Every team is `reachable` unless the user says some repository cannot be cloned; only a team they cannot read is a candidate for `(external: …)`. `capabilities.db_schema.map` is step 3's database projects, one entry per database. An environment named in more than half the deploy files step 3 found is kept without asking; when step 3 found no deploy files, `environments.names` is `[prod]` and nothing is asked. `environments.names` is listed earliest first with a recovery copy of production after it, and `environments.exclude` is every environment step 3 saw that the answer leaves out. A field the list above does not name takes the value the reference shows, except `reader.example_projects`, which is up to three of the most recently committed repositories from step 3, and `repo_dir_map`, which stays empty. A capability the user does not have is set to `none`, which removes its sections from the output.
   - **Asked, in this order, one batch each.** Skill name, what to call the knowledge and which kind of id people sign notes with. Where a project says who owns it, which sets `scope.owner_source` from the places step 3 found plus a choice to be asked per project, which is `none`; when step 3 found no place, `scope.owner_source` is `none` and no place is asked, and a place the user types themselves is taken as the value. Which team owns these projects, free text, the one entry of `scope.owners`, is asked whenever `scope.owners` would otherwise be empty. The environments that half or fewer of the deploy files step 3 found name, as a multi-select, skipped when no environment is that rare. The runtime when step 3 found none, as a multi-select of the four runtimes. Connected tools: one confirmation covering logs, dashboards, the feature-toggle lookup and the wiki, not a question per tool. It is asked only when step 3 found at least one candidate tool, a tool recorded as unreachable included and stated as unreachable; otherwise logs, dashboards, the feature-toggle lookup and the wiki are `none` and step 7 lists them. Its answer supplies `global_settings.lookup` and `external_reference.sources`, and a capability the user names no source for is `none`. The other-tools question shares that batch and is asked whether or not step 3 found a candidate: whether any other tool is used to check facts about a project (a code-quality scanner, a tracing backend, an error tracker, an issue tracker). It offers two choices, no other tool and yes; a yes is followed by one free-text question for each tool's name, what it answers and, optionally, what to record per project to find it, and an other-answer that already names tools counts as a yes. Each named tool becomes an entry of `capabilities.tools`, its `access` the server name when this session sees an MCP server of that name and `none` otherwise; no other tool leaves `capabilities.tools` empty.
   - **How to ask.** Use the user's own language and plain words, built from the reference's `ask:` and `effect:` lines: the question in one sentence, then one clause on what the answer changes in the generated files. A choice's description says only what sets it apart; a clause every choice shares goes in the question once. Name a connected tool by its server name, never by one of its function names. A config key, a preset slug that is not the thing's everyday name, and a term of this skill (reachable, deployed, skeleton, capability) never stand as the question or a choice label. Present a single proposed value for confirmation inside its batch, with its evidence in plain words. A question with a finite answer set offers the presets, named in everyday words, plus an other choice. A question whose answer is which items of a proposed list to keep is a multi-select of those items, with the other choice for anything to add; it never offers an "edit the list" choice. A picker holds at most four choices, so a longer list is split into several questions by a shared attribute, and no item is dropped. The skill name question shows the full name the answer produces (`<name>-knowledge`).
   - **In a revision**, ask once what the user wants to change and change only that. An existing value wins over a default and over the probe, except that an explicit request to detect again makes the probe win for the fields it probes; only the fields the config leaves empty are otherwise decided, and keys the reference no longer lists are dropped.
5. **Validate a draft.** Write the object to a scratch file and run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/render.py" --config <scratch file>`. Without `--write` the renderer only validates and prints a plan, so nothing is written. Fix every error answerable from what the run already knows; ask only when the answer is the user's knowledge. Done when it exits 0.
6. **Write the config.** When the file already exists, show the difference from the draft and wait for confirmation before replacing it; when it does not, write it. Done when the same command on `<repo>/knowledge.config.json` exits 0; cite its `plan:` line.
7. **Hand off.** Report the path written, the fields decided without a question (default or probe, each with its source), and the proposals the user accepted as shown or answered with the other choice (each tool recorded as unreachable named there, and each entry of `capabilities.tools`), then name `/knowledge-generator:generate <repo>/knowledge.config.json` as the next command. Nothing is rendered here. Done when the report contains all three.

Running this again on an unchanged config and accepting every proposal produces the same file.
