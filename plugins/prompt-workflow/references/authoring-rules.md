# Authoring rules — the shared catalogue

**One home for every rule about what a good skill or agent file looks like.** Two skills read this file: `skill-authoring` follows it while writing, `review-skill` audits against it. A rule added here is enforced on both sides without touching either skill.

Each entry carries three things:

- **the rule**, in positive form — what good looks like
- **what breaks** when it is violated — the evidence that earns the rule its place
- **`→ check:`** how a reader sees the violation in the file, or **`→ process`** when it governs what the author does rather than what the file says (an audit skips those, and skipping them is not a gap)

Scope: the artifact and the craft of producing it — never how to converse with the user. How to answer, when to push back, what tone to take is session conduct and lives in a `CLAUDE.md` or an output style, not here.

**Let the important thing be the only thing on the line.** The cost of a note is not its length, it is the attention it takes from what sits next to it: a list carries no priority signal, so the reader cannot tell that one entry matters ten times more than the next, and every low-value line makes the high-value ones harder to find. An unimportant note is therefore worse than free. That sets the bar for adding one — not "is this true" but **"is this important enough to compete with everything already here"** — and it decides what to leave out: how the thing came to be that way, the variations that might occur, the things to keep an eye on, unless one of those is load-bearing by itself. This governs every rule below, and the rules below stop restating it.

**State what is true, never an account of someone arriving at it.** Two shapes, and both leave the reader extracting the rule out of a narrative instead of reading it. *Retrospective* — a rule written as an event in this file's past ("also remember to check Y", "additionally", a line that parses only once you know it was appended) states the edit instead of the subject, addressing the previous author rather than the next reader. *First person* — "I should read X first, then compare Y" narrates an actor working through a plan, so it reads as one imagined run rather than as the contract, and it cannot be checked off the way a stated step can. Deletion is the wrong cure only when the rule is earned. An unearned one is *A note born from one run's slip* below and it goes; an earned one gets rewritten as what holds ("Y is checked before Z"), or as the imperative the step actually wants ("Read X, then compare it against Y"), and moved to where it belongs rather than left at the point it hurt. **Two carve-outs.** A failure recorded as a fact about the world stays — "a bare path resolves against the user's cwd" is evidence, per *Cost* step 4; what goes is a failure recorded as this file's history. And naming the role a duty belongs to ("the orchestrator dispatches X") is a contract, not narration. → check: no rule parsing only as an addition, none narrating what changed or what to remember, and no first-person or should/would plan standing where a fact or an imperative belongs.

## The description is the trigger, nothing else

- **Trigger conditions only** — the situations, symptoms, and phrasings that should reach this skill. A description that summarizes the workflow gets *followed* instead of the body: one saying "code review between tasks" produced ONE review where the body specified TWO. → check: the description holds conditions and phrasings, not a précis of the steps.
- **Enumerate the phrasings the user actually types** — colloquial as well as formal, and in every language they write in, since a description covering only the tidy English wording leaves the everyday ask to model judgement. Cover the *small* ask too ("just fix this one line" must reach the skill exactly like "audit this file" does). → check: everyday forms present, not only the formal verb list — and present in every language its users type, since an all-English enumeration satisfies an "everyday forms" read and still cannot match an ask that arrives in the user's own language.
- **Describe the target by shape, never by naming example skills.** An illustrative `(/a, /b, /c, …)` narrows nothing, collides with each of those skills' own triggers, crosses plugin boundaries, and goes stale on the next rename. → check: no other skill or command named as illustration.
- **State what it is NOT when a neighbour is close** — "prompt files, NOT application code" is what stops the wrong skill winning. → check: a NOT clause exists whenever a sibling could plausibly match.
- **Compress every description by default — and the one thing compression may never touch is the set of situations that match it.** Every description sits in context permanently while the body is lazy-loaded, so this is the one place each word is a standing cost paid on every request; the budget that bites is the **repo-wide sum**, since all of them are in context at once (a hundred at 400 characters costs far more than any single one can). But the two halves shrink very differently: the **phrasings and symptoms ARE the matching surface**, so cutting one silently narrows what can reach the skill, while everything around them — what it does, why it exists, how it works, the connective prose holding it together — costs characters and buys no recall whatsoever. So shrink by deleting the explanation and keeping the enumeration, **telegraphically**: a comma-separated run of trigger phrases beats well-formed sentences at the same recall for a fraction of the characters. Same principle as saving tokens by method rather than by coverage, one layer down. (**1024 characters is the harness's hard cap** — a wall, not a budget; touching it means the description is describing the skill instead of triggering it.) → check: nothing but trigger surface survives a trim; no capability tour, rationale, or restated steps; under 1024 characters.
- **The test that keeps it honest, before and after any trim**: write out the list of situations that should reach this skill, then check both versions against it. A situation that stops matching was **coverage** — put it back. A word that vanished with every situation still matching was **prose** — it was right to go. Without that list, "compress" and "narrow" are indistinguishable, which is exactly why descriptions either bloat or quietly lose their triggers. → check: a pass that trimmed a description names the situations it checked and states that each still matches; one that stopped matching is restored, not argued for.
- **~400 characters is the review trigger, not a limit** — well-formed descriptions land around 200–300, so past 400 the question is "what is this buying?", and the only acceptable answer is recall: a genuinely wide symptom surface, phrasings in more than one language, or a NOT clause a close sibling forces. How much each invocation class needs is settled in *Decide who may invoke the skill* below; what this bullet adds is that **the flag is a floor on the need, not a measure of it** — a skill can own a `/slash` command and still be reached mostly by ordinary talk, and then it needs every phrasing. → check: every description over ~400 characters is over it because of trigger surface, not prose.
- **Decide who may invoke the skill before writing its description — both directions are frontmatter flags, never prose.** There are exactly three invocation classes, and the class fixes what the description must hold:

  | class | frontmatter | reachable by | its description must |
  |---|---|---|---|
  | model-selectable | neither flag | lazy-load on the description, and the user naming it | carry the full trigger surface — conditions, symptoms, every phrasing |
  | command-only | `disable-model-invocation: true` | the user naming it, only | disambiguate it from its neighbours and stop; the model cannot select it, so a phrasing enumeration buys nothing at all |
  | lazy-load-only | `user-invocable: false` | lazy-load on the description, only | carry the full trigger surface, which is now the only thing that can reach it — trimming it as if a command could is what silently makes it unreachable |

  Pick **command-only** for a run that must be deliberate — expensive, side-effecting, or simply the user's call to make. Pick **lazy-load-only** for guidance the user should never have to summon, so it stays out of their command list. Writing either constraint as description prose instead ("never trigger this from conversation") binds nothing and is charged on every request, since the prose *is* the surface selection reads. Setting both flags leaves nothing that can reach the skill at all. → check: no do-not-auto-trigger injunction in a description; no trigger-phrase enumeration under `disable-model-invocation: true`; a `user-invocable: false` description carrying no phrasing enumeration — the mirror failure, and the one that leaves nothing at all able to reach the skill; never both flags at once.
- **An argument's shape goes in `argument-hint`, never in description prose — and only on a skill that actually reads one.** A description is matching surface, or under *Decide who may invoke the skill*'s command-only class a disambiguation line; prose explaining what to pass is neither, so there it is charged on every request and still misses the one place the user reads it, the slash-command picker. A hint buys nothing on a skill the user cannot type, so the lazy-load-only class never carries one; on a skill that reads no argument it is worse than nothing, showing the user a placeholder to fill in. Trimming a command-only description down to disambiguation is what makes this bite — the argument shape has to move here, not vanish. → check: no description explains what to pass (a trigger phrasing that merely contains an argument is not that); every `argument-hint` sits at the frontmatter's top level — nested under another key it is inert data — on a skill the user can type and whose body acts on an argument.
- **Never assert the user's setup as fact.** "You maintain several repos" is false for someone with one, and a false premise sends the agent hunting for something that does not exist. → check: claims about the user's environment are conditional.

## Rules first, examples second — an example becomes the whole permitted set

- **State the rule or shape; add an example only to disambiguate it.** An agent reading a list of examples treats that list as the boundary and does only those — the surrounding generality silently disappears. → check: each rule names the class, not just one instance of it.
- **The usual origin is a conversation.** The user names one case they just hit, and the rule gets written as that one case. Generalize it *before* it lands in the file: what class of thing was that an instance of? → process.
- **Where an example must stay, mark it non-exhaustive and make the rule the load-bearing half** — the rule sentence first, `e.g.` after, never a bare list standing in for the rule. → check: no bare list carrying a rule's weight.
- **The `description` is the exception, and only for phrasings.** Listing the words a user might say *widens* what reaches the skill — matching is not deciding, so extra phrasings add recall and cost nothing in judgement. Everywhere the skill decides what to *do*, the narrowing rule above holds. → check: phrasings enumerated in the description; the cases the skill handles enumerated nowhere.

## Write it structured

- **Use the form the content actually has.** A sequence → numbered steps. A set of independent items → a list. Several items sharing the same fields → a table, or a fixed bullet order, one entry per item. Prose is for the *why* that fits no slot. → check: sequences numbered, item sets listed, same-shaped items in a table or a fixed order.
- **Fixed fields make a gap visible.** When every item carries the same slots (what it is / when it fires / what to do), a missing slot shows up as an empty cell instead of hiding inside a paragraph. This is what stops one entry quietly lacking a rule its siblings have. → check: sibling entries carry the same slots.
- **A heading says what its section decides**, so the agent can reach the one it needs without reading the rest — and so you notice when two sections turn out to be the same section. → check: headings name decisions, and no two decide the same thing.

## Names and paths that resolve

- **Name a step, file, or section by what it does, never by its position.** `step1` / `step2` / `notes.md` carry zero information and go wrong the moment anything is reordered or inserted. `2. Validate the config file` survives a reorder; `step 2` does not. → check: no position-shaped or contentless names.
- **Cite a step by number AND name** — `step 2, the text pass`. A bare `step 4` points at whatever lands there after the next renumber. The number is a coordinate; the name is its identity, and only the name survives a reorder. → check: every step citation carries the name.
- `name:` MUST equal the parent directory exactly, lowercase and hyphens. A mismatch is a silent load failure — the skill simply never appears. → check: compare the two strings.
- **The frontmatter block MUST parse as YAML, which the rule above presupposes** — and the way it breaks is a value containing a colon followed by a space: YAML reads it as a new key, so `name` and `description` are both dropped and the skill loads with empty metadata. `description` is where this bites, because trigger prose naturally contains `word: word`. Quote any value that does — double quotes, escaping only inner double quotes — rather than rewording, so the trigger surface is untouched. → check: run `claude plugin validate <plugin-root>`; reading the line does not reveal it, and a `name:`-matching check passes right through it.
- **A `plugin.json` must not re-declare the conventional `hooks/hooks.json`** — that path is auto-loaded, so naming it in the manifest is a duplicate and the hooks fail to load entirely. The manifest names *additional* hook files only. → check: `plugin.json` has no `hooks` key pointing at the conventional path.
- A bundled-file read needs a base: `${CLAUDE_PLUGIN_ROOT}/…` for plugin-level files, `${CLAUDE_SKILL_DIR}/…` for the skill's own. A bare `references/x.md` resolves against the **user's** working directory and reads nothing, and an `@`-prefixed one force-loads whether this run needs it or not — which defeats the reason the material was extracted. Point at the path and say when to read it. → check: every read instruction carries a base, none uses `@`.

## Steps: name what each one hands the next

- For every step, write down **what it records and who consumes it**. That sentence — "record the range; step 2 reuses it" — is the only thing that makes the break visible when someone later edits either side. → check: each step names its output and that output's consumer.
- **Done-conditions must be checkable**, and exhaustive where it matters ("every changed file accounted for" bites; "produce a list" does not). An unfalsifiable bound lets the agent declare victory early, and it slips hardest when the later steps are already in view. → check: each step's bound is falsifiable.
- **Give a positive target alongside a prohibition**, keeping the ban's force. A bare ban leaves the forbidden behavior as the last pattern the agent read. → check: bans are paired with what to do instead.
- **Every branch needs a landing place**, and a jump must survive its own step being skipped — a "go to step 6" living inside step 2 never fires when a flag skips step 2. → check: every named branch or jump has a defined target reachable on all paths.
- **A step that could ask the user must state on the page which it does — decide, or ask.** Write "ask" only where two readings lead to materially different work, and have the step offer options when it does; anything determinable from what the run already has, the step determines. Left unstated, every such step becomes a question and one task turns into a questionnaire. → check: such steps say which.
- **A step that claims completion names what proves it** — the command it ran, the output it read, the file it re-read. "Done" with nothing behind it is an assertion. → check: completion steps cite concrete evidence.
- **Be exact about the destination, never the route.** A step states its goal, its bound, and the context the agent cannot derive — where the data is, which tool to reach for, a schema it would otherwise guess. It does not script the route: which files to open, which line range to read, what order to grep in, how to recover from one particular error. A written-in route breaks the moment reality diverges from the repo it was written against — "if the diff touches `auth.py`, read lines 40–120" is wrong after one insertion — and prescribing every check turns an agent that can look into a script that cannot. **The test is whether the sentence survives a different repo, a renamed file, or one inserted line**: no → it is route, delete it and state the goal instead; yes → it is a criterion, and every rule above applies to it in full. **This weakens no done-condition** — the goal stays falsifiable and the handoff stays named; what goes is the itinerary, not the destination. **And leaving the route open means the sentence is absent, not hedged**: having said what done looks like, saying nothing about which files is this rule, while "視情況決定要讀哪些檔案" is the failure *Where content lives* bans. **The skill's own bundled files are not a route** — a `${CLAUDE_PLUGIN_ROOT}/…` path ships with the file and moves only when the author moves it, so *Names and paths that resolve* still requires it named exactly. What this rule bans is a path into the material being worked on. → check: no step fixes line ranges, file lists, or counts in the target as if stable, or scripts error recovery; every step that leaves the route open still states a checkable goal.
- **A flag or mode is a branch, not a discount.** Adding one is legitimate when two inputs genuinely need different work — name the condition that selects each branch, and make the run say which branch it took so the user can see the path rather than guess it. What is not legitimate is selling a branch as cheaper coverage: if the only difference is "does less of the same work", that is a saving to find in the flow, not a switch to hand the user. Where a branch does cover less, its output states what it skipped. → check: each flag names its selecting condition; no flag whose only effect is reduced coverage.

## If the skill changes state

Only applies when it writes files, runs git, dispatches work, or produces artifacts — a pure reference skill has no state, and skipping this section for one is correct, not a gap.

- **Say what a second run does.** Re-running after a crash, a retry, or the user simply running it twice must not double-apply work, skip work, or mistake its own earlier output for fresh input. "It depends" means nobody checked. → check: the file answers the question explicitly.
- **Guard anything destructive.** For delete, overwrite, purge, reset: state the guard — a dry run, a confirmation, a scoped path — *before* the action, not after it. And never let "half done" or "never started" be classified as "done" and then discarded; that is how work disappears silently. → check: a guard precedes each destructive action.

## Depending on anything outside the file

- **Keep the skill able to stand alone — then let it use a neighbour it can live without.** Never read a path belonging to another plugin, and refer to any skill by name rather than by path: a path into a neighbour breaks the moment that neighbour is not installed. What that bans is the **hard** form — a cross-plugin path, or a step that cannot finish when the other plugin is absent — and a declared `dependencies` relationship exempts it, since the other plugin is then guaranteed present. **Naming another plugin's skill for the Skill tool is not that**, and is legitimate whenever the absence-plan rule in this section covers it: detection, plus what the run does instead. Treating every cross-plugin mention as a violation is its own failure — it forces a plugin to copy what it could have deferred to. → check: no cross-plugin path; every cross-plugin skill load either sits under a declared dependency or carries its absence plan.
- **Every outside dependency needs an absence plan**: a missing argument, a tool or MCP server that is not wired, a sibling skill that cannot be reached, a file or artifact that is not there. For each, write two things — how the absence is detected, and what happens then (proceed with less, or stop and name what is missing). Put it where the dependency is first used, so it is checked up front instead of discovered mid-flow. → check: each dependency has detection plus consequence, stated at first use.
- **Absence is announced, never silent.** A skill quietly doing less looks exactly like a skill that found nothing. → check: the reduced path's output states what was skipped.
- **When another loaded source states the same thing this catalogue does, this catalogue wins on judgment.** A separate skill or plugin documenting how to write a skill or agent can be in context on the same turn, competing rule for rule, and the one that gets followed is then whichever the model read last. Treat any such source as authoritative only for the harness *mechanics* it documents first-hand — e.g. hook event names, manifest fields, a marketplace schema — and per *A fact that rots somewhere else is cited, not copied in*, cite those rather than copying them here. Naming that source in this file is the one thing not to do: it crosses a plugin boundary, so it breaks the moment that plugin is absent and goes stale on its next rename. → check: no outside authoring source named; every judgment rule traces to this file.

## Editing an existing skill

- **Read the steps either side of your edit before making it.** Almost every broken chain comes from editing one step's text while its neighbours still describe the old handoff — the edited sentence reads perfectly, and the seam is what broke. → process.
- **Know whether the edit preserves behavior, and make the file show it either way.** A restructure is behavior-preserving: same decisions, same outputs, only wording or layout moves — so check the outputs are actually unchanged before treating it as one, because an "optimization" that quietly decides something differently is the worst outcome here and the diff will not flag it. When behavior does change, the change has to land on every surface that documents that behavior — the README, the manifest, the changelog. **Merging or removing a skill, a command, or a flag is always that case**, never a silent cleanup. → check: an interface change appears on the documenting surfaces, not only in the diff.
- **Before changing a rule, grep a distinctive token from it.** A rule usually lives in 3–6 places: its canonical section, a summary table row, a checklist line, a guardrail, the README, manifest keywords. Fixing one and missing the rest is the most common defect there is, and one grep is the whole cure. The same applies to **renaming a term** — every occurrence moves together or the file now says two things. → check: no copy of the changed rule still states the old version.
- **One concept, one term, whole file.** Drifting between synonyms (pass / round / phase; target / file / subject) reads as three different things and the agent treats them as such. Pick the word, then grep the synonyms out. → check: one concept never appears under two words.
- **When you INSERT into a step**, check exactly four things about that step: its declared limits, what it records, who reads what it records, and which gate must precede its actions. Every inserted sentence reads correct on its own — the break is always in the neighbour. → process.
- **When you REMOVE a flag, mode, or step, sweep its skeleton**: its report template, jump instructions, `(x only)` qualifiers, and the sentence that existed only to contrast it. Leftovers imply a mode that no longer exists. → check: nothing left refers to the removed thing.
- **Never delete a rule to tidy up.** Assume it is there because something failed without it; count list items before and after an edit. → check: item counts reconcile across the change.
- **A diff that grows the file is the one visible moment accumulation can be caught, so spend it asking whether the rule was what needed fixing.** Nothing already here catches it. *State the rule or shape* audits whether a **rule** names a class, not whether an added block was owed a line at all; its origin note, the one that would have caught this, is `→ process` and therefore invisible to any audit. So each appended case passes both while being individually justified, which is exactly why a file only ever ratchets upward — measured over one plugin's three largest prompt files, 30 successive revisions shrank twice. So every block an edit adds must be one of three things: a rule stating a **class**; an **exception** the existing rules genuinely do not reach; or **evidence** attached to a rule already present (per *Cost* step 4, a why that records a real failure). A block that is one more *instance* of a rule already in the file is none of the three — widen that rule until it covers the case, and add nothing. Where the added block is reminder-shaped, *A note born from one run's slip* in *Where content lives* carries the finer test for that one case; this rule is the gate every added block passes through, whatever its shape. → check: on a growing diff, every added block is a class-level rule, a real exception, or evidence for an existing rule; none restates a case an existing rule already obliges.
- **When the corrections outnumber the structure, rewrite the section from its stable base.** Every incident adds a line at the point it hurt, and each line is individually justified — the accumulation is what kills the file: the section drifts out of the shape its content now has, and the rules that matter get harder to find among the qualifiers. **Three signals it is past patching**: a rule that only parses if you know the incident behind it, a rule whose job is to correct the one above it, or a heading that no longer names what its section decides. Then rewrite that section — same rules, structure re-derived from what it now holds — instead of appending a fourth qualifier. **Distinct from *a note born from one run's slip*** in *Where content lives*: that deletes a single item that was never owed a line, while this fires when every item is legitimate and the section still has to be rebuilt. → check: no rule exists to correct its neighbour, and no heading has stopped naming its section. A rule that parses only with its own history behind it belongs to the governing *State what is true* rule above, judged per line rather than per section.
- **Do not invent a capability for another role.** If a step says "the agent reports X", that agent's own contract must gain the duty, or nothing reports X and the check silently never runs. → check: every duty asserted for a role exists in that role's own instructions.

## Where content lives

- **`SKILL.md` carries the flow; the knowledge each step applies is a unit that step names.** The flow is order, branching, handoffs, done-conditions — what moves when the procedure changes. The knowledge is criteria, rule catalogues, output formats, domain facts — what moves when the subject matter changes. Woven into each other, an edit to either forces a re-read of the whole file to find where the other leaked, and no step can be pointed at a different body of knowledge. **A unit is a heading or a file** — which one is the extraction question below; that it is addressable as a single thing is this rule, and it holds for material that stays inline. Push too little down and the steps drown; push too much and the agent never reaches it. → check: the steps read as the procedure end to end, and each body of knowledge they apply sits under a name — a heading or a file — rather than dissolved into the step prose.
- **The flow names the knowledge; the knowledge never depends on the flow.** A step says which unit it needs and what to take from it. The unit states its rules — never one conditioned on which step invoked it, never an instruction that resumes the procedure ("then go on to …"). That dependency is what makes a split cosmetic: the unit cannot be pointed at by a second caller, and it cannot be swapped without reading the flow first. A provenance line naming its reader is orientation, not this, and carries the step's name per *Cite a step by number AND name*. → check: no reference or template conditions a rule on its caller or hands control back to the flow; no step restates what the unit it points at already holds.
- **Extract when it buys one of five things**: the material is read only on *some* runs so extraction makes it lazy; it is shared by two or more steps or skills, so one file becomes the single home instead of two copies drifting; it is a bulky catalogue that would bury the steps; or **its effect depends on arriving late in the run** — every run needs it, but read at load it is buried under everything the run has read since, so extraction buys position rather than laziness (a rule that has to win against the model's default at the moment of writing the output is the shape). Sharing one file works within a plugin; across plugins a bundled-file read is a path and stays banned, so the choice there is a lazy named load carrying its absence plan, or a deliberate copy where there is nothing to degrade to. The fifth is **a second owner or a real variant** — a stack pack overriding core's ruleset, a house convention a consumer replaces, a body a sync overwrites — where the separate file is what lets the material be replaced without touching the flow. **Its trigger is a variant or an owner that exists now, never one you can imagine**: extracting on the possibility is the speculative abstraction the next rule bans, and it buys a hop for nothing. → check: each extracted file satisfies one of the five.
- **An open set settles the borderline between the two rules either side of it.** A block not yet bulky enough to bury the steps extracts now when its content is an *enumeration* — cases, rules, criteria, failure modes, one entry per thing the world supplies — because the world keeps supplying them, so it converges on the third reason anyway and the move is cheapest while the block is small. A closed one stays inline however likely an edit looks: a precedence between two rules, a fixed field set, a three-way branch is complete when written, its parts fixed by the structure rather than by what turns up. The test is the shape of the content, readable off the file with no history and no forecast — an accumulating log corroborates it, an intention to add more later is evidence of nothing. → check: every inline enumeration is one the structure closes; every extracted file is bulky, lazy, shared, positional, or owned elsewhere.
- **Do NOT extract what has one reader and always loads** — *and exists only once, does not depend on when it arrives, has no second owner or variant, and is a closed set*. It costs the same tokens plus a hop, and the indirection is a new thing to get wrong. When the same material exists in two places, this rule does not apply; *One canonical home per rule* below does. Nor does it apply to the fourth or fifth reasons above, nor to an open set: there the hop is the point, and what pays for it is position in the fourth, replaceability in the fifth, and in an open set the third reason it is heading for anyway. **Those two carry a cost the other three do not** — the pointer has to be obeyed, so it belongs at the step where the material is used, written as an action rather than a note; a deferred read that never happens is worse than the buried copy it replaced. → check: no single-reader always-loaded reference, unless it is extracted for position — its pointer then sitting in the step that consumes it — for a second owner or variant that exists, or for an open set.
- **Pointer wording is the reliability lever** — imperative, naming what is behind it and when to read it ("Read X now; it holds A and B"). A vague "see the reference" fires on some runs and not others. → check: every pointer names its content and its trigger.
- **A reference is part of the unit, not an appendix.** After extracting, check that whatever selects files — a scope filter, tooling, the audit — still sees the new location, and remember an edit inside it implicates the steps that drive it. → check: file selectors cover the reference locations.
- **A skill that emits a document ships the document as a template file** (`templates/…`) instead of describing its format in prose. The template is copyable, has one home, and keeps the steps short — they then only say when to use it and what to fill in. If the output's language matters, fix it in one place rather than restating it per step. **Precedence when this meets the rule above**: a document emitted on *every* run has one reader and always loads, so it stays inline — extracting it buys a hop and no laziness. Ship a template when the document is emitted on *some* runs, is copied by the user, is long enough to bury the steps, or **has to be read late** — a format the run must follow *against* whatever it has drifted toward by then is the fourth extraction reason, and it outranks this clause. → check: document formats live in template files, not in step prose, unless the document is emitted on every run and does not have to be read late.
- **Write the fact and the condition, not a mood plus caveats.** A rule the reader cannot tell has fired is not a rule: 盡量／視情況／留意／"if needed" leave the decision unmade, so the agent settles it however is cheapest that run. Naming the condition is usually also shorter. **The cause is rarely caution — it is an unverified claim**: not knowing whether a field exists produces "若有的話…先確認", checking produces "that field does not exist on this stream", so the fix is to go and find out, not to reword. **And most often the hedge is how a MUST got downgraded at the point of use while the canon still says MUST** — both instances this rule's first sweep found were that shape (a field the policy marks 必記, written 盡量填 in the very skill that writes it). That makes it criterion (h)'s: restore the force, state the fallback. **Two things that look like hedges and are not** — a **boundary** clause (what the rule is not license for) is a fact about scope; a **tendency with its condition attached** ("prefer X; do Y when Z") is a decision. A preference with no condition is what fails. → check: every rule says when it fires; no hedge carrying a rule's weight — and grep for it in **the language the file is written in**, since a catalogue of English rules audited against a list of Chinese words reports clean on every hedge it contains: 盡量／視情況／留意 on one side, if needed／as appropriate／where possible／try to on the other, plus the self-evidence words that leave the same decision unmade — plainly／clearly／obviously／simply, which read as force and supply no condition. Read each hit against the canon defining that thing.
- **A note born from one run's slip is not a rule — delete it unless it names a real exception.** Something gets written, a later check finds a gap, and instead of fixing the source the author appends "remember to check XX" back at the original spot. If checking XX was already required, the miss was **execution, not specification**: the reminder buys nothing and lowers the baseline by implying XX was not expected before. **One question decides it — would a reader following the rules already there have been obliged to do this anyway?** Yes → delete it, or sharpen the rule that existed. No → it is a real exception or an ordering constraint the neighbours do not state, and it earns its line. **Carve-out against (k)**: k presumes an item was earned by a past failure, which holds for a rule closing a *specification* gap, not for a reminder restating a duty the spec already imposed. → check: every reminder either names an exception or adds a constraint its neighbours do not.
- **An instruction addressed to the file's author does not belong in the file, and scaffolding notes outlive their scaffold.** "Fill the rest in later", "write each entry as one short sentence", a `TODO` — those speak to whoever edits the file, while the cost is paid by every run that loads it. They are also the most durable stale content there is: written when the file was a skeleton, still there once it is finished, by which point the filled-in entries show the format better than any sentence describing it (one survived from a 33-line file with five `_待補_` into a 79-line file holding 33 real rules). Put that guidance where the author reads it and delete it from the artifact. → check: no instruction aimed at the author; no "to be added later" beside content that is no longer missing.
- **One canonical home per rule, and the number of copies is what decides it — never how often the file loads.** A guardrail restating a step's rule in one line is house style; a second full copy of a block is drift waiting to happen. The *don't extract* rule above governs material that exists **once**; the moment the same text sits in two files, give it one home, because the two costs are not the same order of magnitude — an extra read costs a hop, a silent divergence costs a wrong answer nobody sees. Two arguments that sound like engineering and are not: "it always loads anyway, so extraction saves no tokens" weighs the cheap side against nothing, and "only one copy loads per run" is precisely the condition under which the stale copy is the one that fires. → check: no substantial block exists twice.
- **A fact that rots somewhere else is cited, not copied in.** Versions, CLI flags, API and payload shapes, another system's field names, a product's current behaviour — these change with nobody touching this file, so a copy here goes wrong silently while the source moves on, and nothing in the file shows that it has. Point at the authoritative home — the docs URL, the repo file that owns it — and say what to take from it. Where a decision in the file turns on the fact and it therefore has to be inline, name where it came from, so the next reader re-verifies it instead of re-deriving it. **This is not license to hedge**: an unverified claim still gets checked and stated as a fact, per *Write the fact and the condition* above; the citation records where the fact was checked, it does not replace checking it. → check: every volatile external fact is a citation, or is inline with its source named.
- **The canonical home can be a file that is already loaded** — a repo's `CLAUDE.md`, a plugin-level reference every consumer reads — in which case consolidating costs no extra read at all. Look for that before creating a new file. The flip side: an always-loaded file is the most expensive home in the repo, so what lands there has to be needed by every consumer on every turn; anything narrower goes in the file that owns it. → check: a rule in an always-loaded file is one every consumer needs.

## Cost: make it smaller in this order

Bloat is real and so is over-trimming, so the order matters — cheapest, safest saving first.

1. **Change the flow so the words are not needed.** The real wins are structural: a check that makes a whole branch unnecessary, a grep replacing a read-everything sweep, one read serving two layers, a result computed once and reused instead of re-derived per item. This is where the large savings live, and coverage does not move. → process.
2. **Merge near-duplicate wording inside the file.** Three bullets circling one idea, a qualifier repeated on every step, two steps sharing a paragraph of boilerplate — collapse them into one statement in one place. The agent then reads one clear rule instead of three overlapping ones, which also removes the "which of these applies?" hesitation. **The test before merging is whether they fire together**: same situation, same demanded action → merge. Different trigger conditions, different actions, or two distinct vocabularies (two rating scales, two fix policies) → keep both, however similar the words look. Merging those hides one of them, which costs correctness rather than tokens. **Passing that test licenses the merge, never the wording that comes out of it** — what a merge drops is a *clause*, not an entry, so the item count reconciles while the rule quietly changes. So before finishing one, list the clauses of the old text and name where each landed in the new; a clause with nowhere to land was dropped, and it goes back or gets said out loud. **The one failure that check cannot see is an inverted lead**, where every clause does land and the main clause flips — "X is legitimate, just not the default" rewritten as "X is the commonest failure" — which reads as the same rule and steers into over-correction. → check: no two entries demand the same action in the same situation, and every clause of a merged-away entry is locatable in what replaced it, carrying the emphasis it had.
3. **Extract rather than delete** when the material is real — *Where content lives* holds the five things extraction can buy, and only the first of them is "not always needed"; material every run reads still extracts when what it needs is to arrive late. → process.
4. **Then cut the lecture, never the rule.** Delete what teaches a concept the model already has, and delete duplicated prose. **Rationale splits in two**: a "why" that records a real failure ("a bare path resolves against the user's cwd") is evidence and stays — it is what stops the rule being re-litigated; a "why" that explains a general principle goes. A one-line rule is not bloat even when the concept is obvious. → check: no tutorial prose; every rule still present.
5. **Then tighten how the surviving rules are worded — syntax only.** A rule keeps every clause and still comes out shorter: a parallel entry drops the subject and verb the entry before it already established ("early morning she is slow, daytime she was mid-something" → "early morning slow, daytime mid-something"); an appositive "which is the X" becomes "— the X"; "the ones that arrive" becomes "arrive"; a spliced "— but" becomes a new sentence. Measured on two unrelated prompt files, an always-loaded persona and a 500KB workflow, the band came to **0.13%** and **0.02%** of them: it is real and it is close to empty, because a file edited more than once has already spent it. A hand pass that appears to reach 4–5% is step 6's failure counted as a win. **Filler adverbs are the trap, not the band.** Actually, genuinely, simply and really read as padding and in a prompt file almost never are — a prompt exists to stop a model satisfying a rule superficially, so "only when a simpler option genuinely fails" and "the ceiling you were actually given" are both load-bearing, and stripping them widens every rule they scope. Those two files held 244 of them between them; none was removable. **What makes it safe is that nothing is judged surplus**, so the burden-of-proof rule has nothing to weigh. The moment a qualifier goes it is not this step: dropping "closing the line" from "a bare verb stub closing the line" widens the rule from a line-ending stub to any stub, and "a formal noun or verb" shortened to "a formal word" widens it the same way — both read as tightening, and both are step 6's failure wearing this step's clothes. **The test is whether the sentence still answers the same three questions**: which cases match, in what position, under what exception. → check: every tightened sentence matches the same set of cases as before, with no qualifier, position, or part-of-speech restriction lost.
6. **Never buy brevity by shortening a rule into ambiguity.** A rule squeezed until it could be read two ways costs more than the tokens it saved, and the loss is invisible until something behaves wrong. → check: no rule readable two ways.
