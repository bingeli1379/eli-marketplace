# ES query rules (loaded at step 4's GATE)

**Every field name and value below is a ROLE, not a literal.** Resolve each role to this stream's actual field via the per-stream mapping loaded in SKILL.md step 1c (or via the URL's own filter clauses, which already carry the right ones). The concrete names shown are one common shape, not defaults — see "Roles, not names" below.

Required filters on every query:
- `range` on the **timestamp field** (commonly `@timestamp`) — the parsed time range with ±5 min buffer
- an **env filter** — from the URL's filter; the value's wording and casing differ per stream (`prod` on one, `production` on another), so copy, don't normalize
- a **service filter** — REQUIRED; one query per candidate service
- a **severity filter** — REQUIRED. Error+fatal by default, expressed in whatever form this stream uses: a text value set, a numeric severity range, or both. Include warning-level only if the originating alert was warning-level or the dashboard panel includes warnings. Count warning separately from error/fatal.

**Copy the URL's filter clause verbatim — do NOT default to `term .keyword`, and do NOT normalize the value.** Kibana URL filters carry the exact query, e.g. `match_phrase:(<service-field>:<value>)` OR `match_phrase:(<service-field>.keyword:<value>)` — the field path differs per data view, the type is always `match_phrase`. Replicate it as-is; do not "upgrade" to `term <field>.keyword`. Why: many data streams map their service / env / severity fields as plain `text` with **no `.keyword` sub-field**, and a `term <field>.keyword` on a missing sub-field matches nothing → a false `0` with no error (this has burned whole investigations). `match_phrase` on whichever field the URL names sidesteps this, and also absorbs value-casing misses like `"Error"` vs `"error"`. Only build your own `term <field>.keyword` after confirming the sub-field exists (sample one doc with `_source: "*"` or `get_mappings`). For a multi-value filter, use a `bool.should` of `match_phrase` clauses (mirroring the URL's `bool.should`), not `terms`.

**Roles, not names — and the filter field is not always the read field.** The concepts this skill needs (service identity, environment, severity, log text, timestamp, user identity, HTTP path / status / latency) are named differently on every stream. Two consequences: (a) a name that is correct on a sibling stream returns a silent `0` here, which is the most common false zero in this skill — ahead of `.keyword` and casing; (b) a data view can expose **runtime fields / aliases** that filter correctly but are **absent from `_source`**, so a query can succeed while the field you then try to read comes back empty. Resolve both the filter field and the read field from 1c's mapping before writing the query.

**NEVER run a query without a service filter, time range, AND severity filter.** A `*` or `match_all` query is forbidden — past incidents include heap exhaustion from unbounded queries. Severity matters most on a stream that carries **every** level rather than errors only: such a stream can hold orders of magnitude more documents in the same window, so dropping severity turns a scoped query into a full scan.

**DO NOT include `aggs` / `aggregations` — or `script_fields` — in your search body.** The `mcp__elasticsearch__search` wrapper strips aggregation results from responses; only `hits` are returned. Writing an `aggs` block wastes the round-trip — the wrapper accepts the body but drops the results, so you can't see what you asked for.

**`script_fields` fails worse than `aggs`: it turns a working query into a false zero.** The identical filter that returns N hits without it comes back as `Total results: 0` with it — no error, no warning, just an empty result that reads as "this data does not exist" and can end an investigation on a wrong conclusion. So do NOT reach for a painless script to trim the log-text field down to its first line, however attractive that looks against the token budget: pull the bounded hit set and bucket client-side instead (see the dominant-pattern note below). If a query that previously returned hits suddenly returns 0 after you added a projection clause, suspect the clause before you suspect the data.

Use per-bucket queries instead:
- Total counts: `size: 0` **with `track_total_hits: true`** — then read the `Total results: N` line. WITHOUT `track_total_hits: true` the total is capped at 10000, so a real 72k count silently reads as "10000" and every baseline ratio / impact number built on it is wrong. Never use a `count` / `value_count` agg (stripped by the wrapper).
- Top message patterns: `size: 5` sorted by `@timestamp desc`, **read the message out of `_source`** — the message text comes back in every hit's `_source`, so you already have it from your sample. Do NOT try to *filter* on the message field to count patterns (see the dominant-pattern note below).
- First / last occurrence: two queries with `sort` `asc` and `desc`, `size: 1`
- Distinct user counts: see the distinct-user handling in the log-analysis step (cannot use `cardinality` agg)

**Token-budget rules** (the wrapper truncates large responses to a file when responses exceed its limit, costing extra `jq` round-trips):
- **Always start with `size: 0`** to get the total. Only sample after that.
- **`size` cap when fetching the log-text field / stack traces: 5.** A single `size: 100` over error logs with stack traces typically blows the limit. If 5 is not enough, paginate (`from`+`size`) or refine the filter — do not raise `size`.
- **Always pass `_source`** with only the fields you need — named per this stream's mapping. For service distribution request just the service-identity field; for a time check just the timestamp field. Default `_source: "*"` only when you need to inspect schema once. **A field that filters fine can still come back empty here**: runtime fields / aliases exposed by a data view are not in `_source`, so request the underlying stored field, not the alias you filtered on.
- **Dedupe stack traces.** When sampling errors, identify each unique error pattern by its leading message (first line / exception type). Once you have one full sample per pattern, do NOT pull additional documents that share the same pattern — re-reading the same stack trace 5 times costs tokens for zero new information. Use `must_not match_phrase` to exclude already-seen patterns when fetching the next sample — **but only if the message field is actually searchable** (see the dominant-pattern note; on server-log streams where it is not, this clause silently no-ops, so dedupe client-side from `_source` instead).

**Finding the dominant pattern (do NOT trust the first sample)**:
- **DEFAULT FIRST MOVE — bucket client-side in ONE pass, do NOT loop server-side text counts.** Pull one bounded set (`_source` = the stream's log-text field + whatever else you need; let the wrapper dump to a file if it is large) and bucket the leading lines with `grep` / `jq` locally.
- **If the stream carries a pre-interpolation message template, bucket on THAT instead.** Some structured-logging pipelines emit both the rendered text and the template it came from (the template still holding its `{placeholder}` tokens). The template is an **exact** pattern key — identical events collapse onto one value with no leading-line heuristics, no fuzzy grouping, and no risk of splitting one pattern across many buckets because an id or a timestamp got interpolated into the rendered text. Where 1c's mapping names such a field for this stream, prefer it as the bucketing key and keep the rendered text only for the one full sample you quote. Where it does not exist, fall back to leading-line bucketing above. That is a single round-trip and it gives you the whole distribution at once. Firing N separate `size: 0` `match_phrase` message counts (one per candidate pattern) is the wrong reflex: each is a round-trip that eats the ≤2–3 concurrency ceiling, AND the message field tokenizes camelCase / dotted identifiers unreliably (`PaymentApi`, `CheckoutEntryProxy`, `RedeemAuthorizationCodeAsync` can all silently return `0` even though they are right there in `_source`). Reserve server-side counts for *confirming one specific share after* client-side bucketing — never as the primary weighting loop.
- The first message you sample is NOT necessarily the dominant pattern — recent errors are biased toward whatever fired most recently, not most often.
- **Weight patterns from `_source`; do NOT filter on the log-text field.** In filebeat-style server-log data streams the log-text field is typically stored-but-not-analyzed (and has no usable `.keyword`), so `match` / `match_phrase` / `wildcard` on it silently return **`0` even though the text is right there in `_source`** — a false negative that can make a 100-hit pattern read as "0 weight". You do not need to query it anyway: the text came back in `_source` on the hits you already sampled. To weight / classify, pull the bounded hit set requesting that field and bucket the leading lines **client-side** (`grep` / `jq`); if the set is large enough to blow the token budget, let the wrapper dump to a file and `grep` / `jq` that. Classify by a structured field (message template, endpoint, logger, exception type) when one exists.
- Only once you have **confirmed the log-text field IS searchable** — a `match_phrase` on a substring you just saw in `_source` returns non-zero — may you weight patterns with `size: 0` `match_phrase` counts. **Never conclude a pattern's share from a text query you have not proven returns non-zero on a known-present string.** The same proof is what validates a negative / exclusion clause on that field (SKILL.md step 2b): unproven, it silently matches nothing and excludes nothing.
- If a candidate covers a meaningful share (e.g. ≥10% of total), treat it as a main pattern; if <10%, drop it (client-side, or `must_not match_phrase` when searchable) and look again.
- This avoids two failure modes: "first sample was 2/2151, agent built whole report around it" AND "`match_phrase` on message returned 0, so I assumed the pattern didn't exist".
