# Reviewer Analytical Depth

The **Analytical depth requirement** every reviewer dispatch must carry, plus the two things the dispatcher settles before composing it. Single source for `/apply` (Phase 2 initial run AND every fresh-review retry round), `/quick` (all complexity tiers), and `/review` (every lens dispatch, one copy per agent when the scope is sharded).

**Who gets it:** `review-engineer`, `security-engineer`, `qa-engineer`.

**Who must NOT get it:** every implementation and fix agent (Backend / Frontend / Python / Godot / Electron / Database / DevOps), `performance-engineer` (next paragraph), and the Phase 3 `technical-writer`. They are executors — a coverage declaration there produces over-engineered code and padded docs. This exclusion is the reason the block lives here rather than in `agent-guidelines` (which every agent loads eagerly).

`performance-engineer` stays excluded even when dispatched as a reviewer in its own right (Phase 2's conditional 4th reviewer, or `/review`'s `performance` lens): its own agent file already prescribes a per-data-path verdict table (anchor / growth driver / verdict / degrade threshold), which is its coverage discipline. Layering this block on top would duplicate that structure rather than enforce it.

**That exclusion covers the whole block, the criteria-loading directive included, and that is deliberate rather than an oversight.** External review criteria ration reading depth across a diff, while its pass must be exhaustive over one object and cannot judge boundedness at hunk depth — so the budget would cost it coverage, and its verdict table has no room in a findings-only layout for the SAFE rows that *are* its deliverable. The one part of such criteria it genuinely needs, a project's own always-read / never-read paths, reaches it another way: `config.yaml` is forwarded verbatim into every worker dispatch, and its own file states how it honours each list — widening on always-read, and recording a never-read data path as an unassessed row rather than dropping it.

**Rationale:** a reviewer that names what it did not read has declared its scope; one that names nothing has silently chosen it, and the report reads the same either way.

**A returned report that violates these requirements gets bounced, not papered over.** Severity is what decides whether the run stops, and the not-covered statement is what makes silence mean coverage — so a finding with no severity, or a report with no scope statement at all, leaves a verdict that cannot be acted on. Send it back to the same agent with `SendMessage` naming the missing part; its context is intact, so this is far cheaper than a re-dispatch, and cheaper than assigning the severity yourself — a dispatcher-invented severity is a guess wearing the reviewer's judgement. Observed: a security report returned one finding with no severity and the round was accepted anyway.

**Before composing that block, two things the dispatcher settles and the reviewer never can.** Neither goes into the prompt below; they are what makes the prompt worth sending.

- **Resolve cross-repo questions BEFORE dispatching.** A reviewer's scope is the repo it was bound to, so a question that can only be settled in another repo comes back unresolved every round no matter how many rounds run — who else consumes this shared library, whether any caller constructs it directly instead of through the sanctioned entry point, whether a contract is relied on elsewhere. Answer those yourself and hand the answer over as context. Discovering after two rounds that a grep would have settled it costs both rounds.
- **The prompt carries only what you verified; everything else is asked, not asserted.** A premise stated as fact and later found wrong spends that reviewer's coverage correcting you instead of reading the diff, and it can steer the whole review — observed: a dispatch asserting the change removed a network call from a failure path, when that path had always been in-memory. State what you checked, and for what you did not, ask the reviewer to establish it.

---

Include the following verbatim in each reviewer's dispatched prompt:

> **Analytical depth requirement**
>
> **Before reading anything, take the project's review criteria if there are any.** If a `review-criteria` skill is available to you, load it with the Skill tool now — try the bare name first, then the plugin-qualified `code-review-workflow:review-criteria` if that does not resolve. Try both before concluding there are none: it ships in a separate plugin, so an unresolved name and an uninstalled plugin look identical from here, and reporting "no criteria" while they sit installed is the worse of the two errors. If neither resolves, skip it — this block and your own report format stand on their own — and say so in one line, so a run with the criteria is distinguishable from a run without them.
>
> **What loading them changes, and the four things it does not.** They outrank this block and your own report format on **reading depth, the bar an item must clear, the shapes items take, the section layout, and the counting lines** — rendered as they specify, so do not reshape their output into your usual format. This block then supplies only what they leave open, the numbered requirements below. Four things stay yours, because they never claimed them:
>
> - **Your dispatched scope** — which files are yours, and your own shard when the review was sharded — was settled by whoever dispatched you. Their depth rules choose how deeply to read *within* that set, never which set it is.
> - **Severity** survives their layout. A criteria set may sort items by how well demonstrated they are and give each its own field set; every reported item still carries `blocker` / `major` / `minor`, because the workflow that dispatched you branches on exactly that word to decide whether another review round is owed. A layout with no severity slot means you add one, not that severity is dropped.
> - **Cross-reviewer merging.** Their duplicate-merging covers your own findings only; merging across reviewers happens after you, so never reach for another reviewer's items.
> - **The source of a project's own always-read / never-read path list is `config.yaml`, never the project's prose docs.** Criteria that send you to an `AGENTS.md` / `CLAUDE.md` are asking for something this workflow forbids — `config.yaml` is its only trusted project context. Read the lists off it if it declares them — today's `/setup` schema writes no such key, so in practice their project-list state is `none found`, and that is the answer rather than a reason to keep looking. Do not go looking in a prose file for it. The paths still take whatever precedence the criteria give them: what is redirected is where the fact comes from, not the rule.
>
> **Report in Traditional Chinese**, leaving code, identifiers and quoted snippets verbatim. That is this workflow's language, and it settles the language of whatever headings and labels the criteria's own layout asks for.
>
> 1. **State your scope in one line, before the findings** — the file set, diff range, or shard you were dispatched to read. For `qa-engineer` the scope is a scenario set, and its source is fixed by the run: the spec's WHEN/THEN clauses when the target has one (`/apply`, and `/review` when its e2e gate found a covering spec); the acceptance criteria the user supplied when it has no spec but they gave one (`/review`'s ad-hoc path); otherwise every affected user-facing flow (`/quick`, and `/review`'s smoke-only path — labelled NOT acceptance, and the report says so).
> 2. **List what inside that scope you did NOT examine, or examined at reduced depth, and why** — a file you could not read, a scenario you could not run, a check blocked on a `NEEDS:`. Everything in scope and not on this list is taken as covered at full depth for your lens, and the dispatcher holds you to it. Write `無` when the list is empty. Do not enumerate the categories you did cover — a category with nothing to report gets no line; reasoning belongs on the findings (requirement 3), where it is acted on.
> 3. **Severity-rank every finding** — `blocker` / `major` / `minor`, each with a one-line rationale. Raw observations without severity are rejected.
> 4. **Deliver the report as a file when this run has somewhere to put one.** Requirements 1–3 plus a criteria set's own layout overrun the reply size limit on a real change, and a reply cut off mid-finding loses precisely the part the dispatcher acts on — three of six reviewer reports on one measured run came back truncated. **This changes where the report is delivered, never what it contains**: your own agent file's Report Format still governs its sections, its anchors and its wording, and it is that report which goes in the file.
>    - **The dispatch names a change directory** (a spec-driven run) → write the report to `<that directory>/reviews/<your dispatched name>.md`, creating `reviews/` if absent, and reply with the verdict, the range you covered, a count per severity, and that path.
>    - **It names none** (a fileless run — `/quick` writes no artifacts, and a standalone review has no change of its own) → there is nowhere to put a file, so reply with the report itself, ordered **findings first, scope and not-covered list last**, so that a truncation costs the half the dispatcher can re-derive rather than the half it acts on.
